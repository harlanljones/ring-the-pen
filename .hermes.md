# Hermes project rules — ring-the-pen

Hermes: when working in this repo, adopt this behavior. `AGENTS.md` (repo
root) is the operating manual — commands, layout, invariants, boundaries.
This file adds Hermes-specific conduct; do not duplicate it, layer on it.

## Session behavior

- Read `AGENTS.md` in full before your first code edit. It carries the
  seven PRD falsifiers, the frozen pins (k=20, N=3, universe A), and the
  verified command set — do not re-derive any of it.
- Before starting new work, check `ROADMAP.md` for the next unblocked work
  item and its dependency wave. Build the roadmap's items, not whatever
  seems interesting. If the user asks for something out of order, note
  where it lands and record it in ROADMAP.
- `docs/decisions/` is append-only: a decision is changed by a new record
  that supersedes it, never by editing an accepted one.
- Boundary discipline (AGENTS.md §Non-negotiable): math in code only, Jev
  never computes, pitch-count stop is a code gate, missing pitch count is
  unknown (never 0), Retrosheet is never live, no public Stats API live
  feed before D6, no lock no demo, precomputed-only joins. Decline
  requests that violate these with a pointer to the rule unless the user
  overrides explicitly.
- One writer per component (AGENTS.md §Architectural ownership): if a
  change lands in a file another owner owns, request it instead of
  editing.

## Skill routing (Hermes skills — load with skill_view before the task)

Run Hermes for this repo via the repo-root **`./dev`** script — the
primary entrypoint for development here. It is idempotent: it creates the
**rtp profile** (`hermes --profile rtp`), prunes irrelevant skills from
that profile via `skills.disabled`, bootstraps the repo-local project
skills in `.hermes/skills/`, and ensures the repo is trusted — then drops
you into a session. Subcommands: `./dev setup` (bootstrap only),
`./dev doctor` (verify environment), `./dev -q "prompt"` (one-shot; all
other args pass through to hermes). The default profile keeps the full
catalog for everything else.

| Task in this repo | Load skill |
|---|---|
| Writing any new feature or fix (Elixir or ETL) | `test-driven-development` — tests first; pure functions in small modules with ExUnit tests beside them |
| A bug that isn't immediately obvious | `systematic-debugging` — root-cause before fixing |
| Before committing code changes | `requesting-code-review` — static scan → gates → independent reviewer → fix loop. Mandatory for multi-file changes |
| Messy milestone chunk just landed | `simplify-code` — run after each milestone, not mid-milestone |
| Validating an unknown design before building | `spike` — throwaway experiment first; findings go in docs/, never half-landed code |
| Calling TypeSafe Jev via the local jev CLI | `jev-tooling` |
| TypeSafe Jev schemas/units of AI work | `typesafe-ai` |
| Executing an approved plan (multi-task) | `subagent-driven-development` — fresh implementer subagent per task, two-stage review |
| Plan interview before implementation | `grill-me` — invoked by the user, but expect it even after "go" |
| "How big is the codebase" metrics | `codebase-inspection` |
| PRs, issues, reviews on the GitHub repo | `github` |
| Debugging ETL Python (`scripts/**`) | `python-debugpy` |
| Bash scripts in `scripts/` or `Makefile` targets | `shell-portability` |
| Substantial autonomous/multi-step work | `unlazy` — keep working to verified done, no stubs |
| Hermes config/theming questions | `hermes-agent` |

Negative controls — do NOT load a skill for a near-neighbor ask:

- A one-off question about Jev ≠ `jev-tooling` (that is the CLI-calling
  workflow); answer directly.
- An ordinary reproducible bug ≠ `spike`; spike is for validating an
  unknown *design* before building, not debugging.
- A failing test in existing code ≠ `test-driven-development` from
  scratch; reproduce, then `systematic-debugging`.
- Doc/comment wording tweaks load no skill at all.

## Hooks (rtp profile)

Configured in `~/.hermes/profiles/rtp/config.yaml`, scripts in
`~/.hermes/agent-hooks/`:

- `rtp-git-guard.sh` — pre_tool_call on `terminal|execute_code`,
  fail_closed: blocks mutating git (push/pull/commit/merge/...); read-only
  git passes. Commit through the user or with explicit approval.
- `rtp-formatter.sh` — post_tool_call on `write_file|patch`: runs
  `mix format` on edited `.ex`/`.exs` files, resolving the repo root
  upward from the edited file. Guarded no-op when mix or mix.exs is
  absent.
- `rtp-evidence.sh` — post_tool_call on `terminal`: appends a compact
  JSONL line per command to `~/.hermes/agent-hooks/rtp-evidence.jsonl`.
- `rtp-inject-git-status.sh` — pre_llm_call: injects branch + dirty-file
  status when the session cwd is inside this repo (matched by checkout
  directory name `ring-the-pen` — this repo has no origin remote).

First session start may prompt for per-profile hook allowlist consent, or
run `hermes --profile rtp --accept-hooks` once.

## Engineering gates (do these yourself, unprompted)

- Every change: `mix format --check-formatted && mix compile
  --warnings-as-errors && env -u TYPESAFE_API_KEY mix test` must be green
  before declaring done (commands verified as of RTP-01).
- ETL changes: `make verify-inputs && make data &&
  python3 -m unittest discover -s tests -v` must pass; `make data` output
  must stay byte-identical unless the change intentionally regenerates a
  derived artifact.
- No derived artifact is trusted until it passes the catalog boundary
  (`lib/ring_the_pen/catalog.ex`).
- Never commit bulk raw data, keys, or `.env*`; raw Retrosheet stays out
  of the repo.
